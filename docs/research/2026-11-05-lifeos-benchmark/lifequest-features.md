## 12. UX and design-system patterns

**Three square panes on a mat.** The studio is `.nav-rail`, `.shell__main` and `.chat-panel` abutting on a 12px canvas mat. The rail wears the mat and runs to the window's top edge; the sheet and dock wear the page canvas; day/night invert the elevation ladder (at night the page is the deepest surface and cards step up). The domain lens moved out of a sheet top bar into the title bar as a page-painted tab with flared bottom corners — the strongest recent example of "chrome follows the page" (`DESIGN.md:5-15,62-66`; `WindowTitleBar.tsx`).

**One box, not two.** Every markdown surface — doctrine, Daily Note, review, Ideal State, project context — is `LiveMarkdownEditor`: the file renders as prose and only the caret paragraph is raw source. A named rule forbids adding a preview pane beside it, because two surfaces that show the same file can disagree (`DESIGN.md:31,60`; `07-doctrine.md:99-100`). This is the single most distinctive interaction decision in the product.

**Boards, not dashboards.** The Dashboard is a pin board per lens with six system cards (goals, deadline, today-week, pending decisions, recent log, doctrine progress), page pins and view pins; cards are arranged by drag or by keyboard (Enter to lift, arrows to move, Enter to drop, Escape to cancel), resized from card borders, and can be handed to the chat as context. Locking the board is a page lock, not a permission system (`types.ts:1152-1205`; `06-dashboard.md:99-159`; `LAWS/DASHBOARD.md`).

**Lens vs wing.** Wings filter navigation; the lens filters data. Every page names which one it obeys, and the two laws are explicit (`LAWS/WINGS.md`, `LAWS/DOMAIN-FILTER.md`). This avoids the common Notion/Obsidian confusion where a sidebar selection silently changes what a page means.

**Calm scale and state colour.** Radii are 6/12/18/24/pill; red/green/blue/amber mean state, not decoration; no Radix; cards draw their own single shell. Deliberate named exceptions (Decisions cards, Daily Note's raised act, settings rows squaring their buttons) are recorded in `DESIGN.md:33-58`, which is unusual discipline for a project this size.

**Operational truth in the UI.** Every failure has a named surface: companion setup card per state, vault-open errors under the buttons, *Files changed on disk* banner with Reload, update dialog that never says "up to date" when it could not check, and inline refusals instead of silent clamps. This matches `PRODUCT.md:27` and is consistently implemented.

**Tone.** Quiet prose, no gamification, no scoreboard, no gauges; deadline pressure is the one deliberate exception (`VISION.md:92-96`).

## 13. Notable engineering decisions (and their trade-offs)

1. **The vault is the database, and the engine is a pure library.** `packages/vault-core` has no Electron imports and takes a root path; it owns paths, create/open, records, SQLite books, the log and the MCP tool definitions. Trade-off: the renderer cannot touch disk (good) and the app cannot exist without a filesystem-shaped contract (also the product). It is also why E2E rigs can drive the real engine (`30-system-architecture.md:129-155`).
2. **One write queue, two write doors, one revision counter.** `vault-service.ts` serialises every engine call; `data-revision.ts` classifies IPC channels explicitly (`MUTATING_CHANNELS`) and MCP tools by inversion (`READ_ONLY_TOOLS`, everything else is a write), then coalesces one `vault:dataChanged` per frame. The documented bug it fixes — "agent logged an expense and the card did not repaint" — is a good example of fixing the actual cause (no one asked the query to rerun) rather than adding polling (`30-system-architecture.md:267-292`).
3. **Decisions are files plus an apply switch.** A proposal is `.lifequest/decisions/<id>.json` carrying a typed target and proposed body; `resolveDecision` is the only approval path, and it re-validates the target before writing. Trade-off: 16 target kinds and a large `decisions.ts` (~1,800 lines), but the inbox is fully offline, diffable and repairable.
4. **Locks instead of an agent sandbox.** The product chooses a small number of operator-only locks (doctrine, library note, review, dashboard) and a single proposal queue, rather than granting the model a scoped token set. Trade-off: more Decisions on agent activity; benefit: a small, testable authority model.
5. **SQLite for rows, JSON for portability.** The live book is `domain.sqlite`; `books.json` is the git-portable form and the only restore source, always with an explicit confirmation and a `.bak`. Trade-off: two representations and a manual export step; benefit: no hosted DB and no binary merge surprises.
6. **Companion as a host, not a library.** Hermes is discovered on `PATH`, the `lifequest` profile is wired, the app attaches to a running gateway or starts one, and never kills a host it did not start. Trade-off: a hard external dependency and seven named failure modes; benefit: memory, skills and transcripts are not reimplemented.
7. **E2E as the only test mechanism.** 72 real-Electron rigs with JSON+screenshot artifacts, four intentionally excluded because they touch a real vault or network. Trade-off: slow, bench-dependent, and no CI; benefit: every claim is measured against the shipped UI, not a mock (`31-development.md:110-153`).
8. **Update trust chain as a product invariant.** The renderer cannot name a URL; main decides the asset, requires size, re-checks the host after redirects and asks the human in a native dialog. Trade-off: no silent/background installs; benefit: the one executable the app runs is the one the operator was shown (`29-security.md:163-203`).
9. **Docs as contract, with laws.** `LAWS/` defines observable behavior, `VISION.md` is an acceptance policy with explicit refusals (no SaaS, no habit scoreboard, no mobile as the product, no hosted ledger). Trade-off: wiki drift is a real maintenance cost (see §14); benefit: scope decisions are arguable against written invariants.
10. **Boring, dependency-light stack.** Plain React + Vite + Electron, no state library beyond React context providers, no UI kit, no server. The entire product is 165k lines with an empty runtime dependency list; the complexity budget goes to vault-core and the electron host instead.

## 14. Limitations, rough edges and missing pieces

**Not present at all (verified by search, not just absence from the wiki):**

- **Global search / command palette.** No `Mod+K`, no cross-vault search, no backlinks panel or graph. Local filters exist only for Pages titles, the chat list, Settings and the note strip.
- **Notifications as a system.** Exactly two native OS notifications exist: deadline pressure (`main.ts:1200-1240`) and a release while the window is unfocused (`main.ts:1532-1560`). There is no inbox, no snooze, no per-feature reminder, no task due date at all.
- **Habits / streaks.** Explicitly "welcome as its own Execute page" in `VISION.md:74-75`, not built. No habit record, no streak anywhere.
- **External calendar sync.** `VISION.md:57-58` wishes for a two-way week sync with conflict prompts; no calendar provider, OAuth, CalDAV/ICS code exists.
- **Mobile/phone client.** `VISION.md:79-83` describes a phone that queues a draft transaction and shows a metric; only `apps/desktop` exists. The phone is not shipped.
- **i18n / locale switching / non-Gregorian calendar.** All copy is English and dates are Gregorian/local; no i18n framework or message catalog.
- **Multi-user, sharing, household accounts, cloud sync, remote vault.** Refused by `VISION.md:110-120` and `LAWS/IDENTITY.md`; no sync client, no server.
- **Importers from Obsidian/Notion/Markdown.** No vault importer; the layout is deliberately not an import format (`VISION.md:28-32`). The only import is CSV/PDF into a domain database.
- **Analytics / trends / scoring.** No aggregation over time beyond view blocks, review snapshots and goal pace; no "how was my quarter" chart, no correlation, no scoring.
- **Recurring tasks / reminders / snooze / due dates.** Tasks have no date field of their own except `links.date` (a link, not a due date) and no recurrence.
- **Clock/schedule drag and keyboard slot movement.** Daily Schedule is type-the-minute then Apply; documented as deliberate (`13-daily-schedule.md:119-121`). Also no date switcher (today only).
- **Kanban/calendar database views, gauges.** Five view presentations only; gauges explicitly refused (`LAWS/DATABASES.md:17`).
- **Database schema lifecycle in the UI.** No rename, no delete, no column delete, no reorder (`19-data-and-databases.md:214-221`).
- **PDF extraction.** The engine can accept extracted rows; the Data page cannot extract (`19-data-and-databases.md:222-224`).
- **Whole-vault encryption.** `VISION.md:22-23` says welcome, on by default; not implemented — vault is plaintext (`04-the-vault.md:230-237`).
- **Signed installer / signature verification.** Explicitly the missing anchor in the security sweep (`29-security.md:200-203`).
- **Past-review browser, review list screen.** Reachable only with the pager; the vault index is for the companion (`18-reviews.md:97-99`).
- **Agent tools for the non-script page blocks, kit install, live-day prep, whole-week-sync.** The engine can render Page/Finance-kit Decisions, but no shipped tool files them; there is no live-day tool, so "prepare tomorrow's schedule overnight" from `VISION.md:65` is not possible.

**Docs that overstate or lag (the important ones for the report):**

1. **Wiki pinned at 0.2.0 while shipping 0.2.5**, so it misses: Images (whole page + vision board), Settings Keyboard and Decisions tabs, batch **Approve all**, the wing renamed Act, hourly update watch + OS notification, project idea-provenance fields, chat tab restore, the global (unfiltered) Decisions inbox, and the page lock's move into a three-dot menu.
2. **Wiki §17/§19/§23/§28 describe the `autoApproveInserts` allowlist as live.** It was retired in 0.2.1; code keeps the field only as a legacy key and Settings → Hermes now has a **Database writes** row (`SettingsHermes.tsx:240-246`; `database-tools.ts:642-670`). `LAWS/DATABASES.md:8-14` was updated to the new policy and is correct.
3. **Wiki §19 says `upsert_row`/`insert_rows` file a Decision except on the allowlist.** In code, new databases, new rows and batch inserts apply directly and are logged; only updates, deletes and `add_column` file a Decision (`database-tools.ts:642-670`; 0.2.1 release notes).
4. **Wiki §23 says the domain lens filters the Decisions inbox.** Code is global since 0.2.1; only the Dashboard's Pending decisions card is lens-scoped (`DecisionsInbox.tsx:170-176,396-398`).
5. **Wiki §27 says the update check runs once per launch with no background poller.** Code runs a one-hour watch with a coalescing tick and an OS notification when unfocused (`updater.ts:573,627-668`; `main.ts:1532-1560`). README is the current text here.
6. **Wiki §28 says nine settings tabs.** Code has eleven (adds Keyboard and Decisions).
7. **Wiki §03/§05/§33 calls the fourth wing "Execute".** The shipped label is **Act** (`wing.ts:17`).
8. **Wiki §12's project schema lacks `projectType`/`source`/`sourceUrl`** shipped in 0.2.5 (`projects.ts:302-357`).
9. **`README.md:139-145` describes Settings → Hermes base URL / API key / Test connection fields.** The wiki and code both say those fields do not exist; the gateway URL and key come from the profile (`28-settings.md:164-171`).
10. **README says "Private / unpublished"** while the GitHub repo is public and `package.json` is `UNLICENSED`; GitHub reports no license at all. Decide and state the license before any public-facing claim.
11. **`VISION.md` features the product does not have** (habit page, calendar sync, phone, vault encryption, overnight schedule prep, signed installer). These are accepted as future scope, but an operator-facing report must not read them as current.

**Rough edges that are visible in code/tests rather than docs:** the Hermes-agent scan uses legacy endpoints that may not exist on a current host (`25-personnel-and-agents.md:200-207`); the companion bearer has no rotate/revoke UI; no single-instance lock; the egress DNS double-resolution caveat; `vault:open` trusts a renderer-supplied path; several E2E artifact reports are stale failures from older harness models, so the suite's current green/red state is not summarisable from the directory alone.

## 15. Top 15 takeaways for LifeQuest (adopt / adapt / defend / ignore)

| # | Takeaway | Stance | Why (in engineering terms) |
| --- | --- | --- | --- |
| 1 | Vault-is-identity, plain files, contract layout | **Defend** | It is the product's moat and its trust story; competitors can copy features but not the "the folder is the database" guarantee plus a 4,000-character agent context bound to the page. Keep the layout documented and versioned. |
