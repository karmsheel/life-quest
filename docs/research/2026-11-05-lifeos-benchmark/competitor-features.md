## 12. UX and design-system patterns

The shell is a set of separately built documents behind one navigation. `public_html/index.html` is a 115-line module entry that hosts Focus inline and mounts ten iframes; `assets/os.js` wires routing, cross-frame `postMessage` deep links, theme propagation and the account chip. That decision buys strict app isolation (each workspace owns its DOM, CSS, scripts and storage keys) at the cost of duplication: nine CSS files totalling ~7,300 lines, repeated dialog/empty-state/toast patterns, three separate i18n passes (static `apply()` walks, dynamic `t()` calls, per-frame string dictionaries) and a theme-sync MutationObserver. It works, and it is why the product could grow to 11 apps in eight weeks, but it is not a design system in the component sense — it is a shared CSS token file plus conventions.

Visually, the product has a coherent dark-first "calm dashboard" identity: a token layer in `assets/base.css` (background `#0a0a0b` overridden later by an EdiFinance palette `#05070a`/jade `#39e6ad`), accent purple/blue, generous radii, subtle gradients, inline SVG iconography, hand-rolled charts (`dashboard.js` builds smooth-path SVG area/bar charts; `weather.js` builds its own weather illustrations with per-instance SVG gradients), and a genuinely lovely time-of-day Focus landscape driven by CSS custom properties. The duplication is visible: `base.css` defines `:root` twice with different palettes ("EdiFinance design-system alignment"), so the token source of truth is ambiguous and apps inherit whichever block wins.

Interaction patterns are consistent and thoughtful: modal `<dialog>` with focus management (17 `showModal` call sites), `aria-live` status regions (17), a skip link on the dashboard, `aria-pressed`/`aria-current` on toggles and nav, keyboard shortcuts in Todo (`/`, `n`, Escape), Notepad (`Ctrl+B/I`, toolbar), Notes (Space-drag pan, Ctrl+wheel zoom), Growth (Enter/Escape in inline goal-task editing), and reduced-motion support in base/dashboard/os/finance/goals/kanban CSS. Empty states are written as coaching copy ("Start with one small step", "Your first review starts here"), toasts carry undo for Todo completion and clear-completed, and destructive actions confirm (habit delete states that check-in history goes too). Loading failures are usually explicit ("Unable to load habits. Refresh to retry."), not silent — a trait worth copying.

Localization is the most distinctive UX layer: English strings are the dictionary keys (`i18n.js:26-31`), Persian loads `assets/i18n/fa.json` (1,664 entries) with `fa-IR` locale, Persian digits via a digit-replacement helper, RTL `dir` on the document, and a Vazirmatn font override for all RTL text; the language is stored per account and a change reloads the whole workspace. Jalali is a per-user display preference for Habittify months/day labels (stored dates stay Gregorian), and the Persian finance periods are a separate product decision (always Persian months). Notepad goes further with per-block direction detection so mixed Persian/English notes read correctly and code stays LTR. The gaps are equally instructive: 15 strings are still untranslated (`tests/i18n.test.mjs`), Arabic is offered in the Settings language list but has no dictionary (selecting it gives English text with Arabic digits/RTL), some hardcoded English remains in chart/dialog copy, and `README.fa` says eleven workspaces while English says ten.

Mobile is responsive rather than native: `viewport` on every page, a modal nav under 900 px, stacked Settings/Growth layouts, horizontal-scroll habit grid, fullscreen Notepad and Calendar defaulting to Schedule under 800 px. There is no PWA manifest/service worker for the app, no offline mode, and browser notifications only fire while the tab is open (due-alerts has no service worker), which is an honest ceiling but a ceiling nonetheless.

## 13. Notable engineering decisions (and their trade-offs)

**Hybrid persistence: SQL tables where relations matter, JSON documents everywhere else.** Habit logs, categories, attachments, mail, users and notepad history are relational; Focus, Finance, Goals, Kanban, Notes, Notepad content, Todo, Growth and themes are whole documents in `app_state`. The payoff is speed of feature delivery: a new workspace is a new document key plus UI. The cost is that whole-document writes with 2 MB caps, no partial updates, no cross-document queries and no server-side validation of document schemas (each domain library validates only the shapes it owns). It is the single decision that most shapes what the product can and cannot do.

**Revision-based compare-and-swap instead of merge.** Every save is `sha256(current)^{revision}`; mismatches are 409 and the client stops saving that document until reload, telling the user to copy their edits. This is correct and simple (it prevents the classic stale-whole-document overwrite) but hostile under concurrent editing: a second tab, a phone, or an MCP write invalidates the first tab's in-flight edits with no merge path. Multi-document mutations (`mutate`, `mutateItems`) extend the same idea transactionally across e.g. a commitment decision plus its ledger entry — the best-engineered concurrency work in the repo.

**Row locking in sorted key order.** `StateStore::mutate()` inserts placeholder rows for absent documents, then `SELECT ... FOR UPDATE` in `ksort` order, so concurrent multi-document transactions cannot deadlock and missing rows are initialised under the same lock. This is a small but genuinely expert detail; it is also why the "API writes use transactions and row locks" README line is true rather than aspirational.

**Iframes as an app-isolation boundary.** Each workspace is a standalone page with its own CSS/JS and its own storage keys, loaded lazily into the shell. It lets separate contributors work on separate apps without a bundler or a router, and CSS/DOM cannot leak between apps. It also means the shell has to coordinate theme, language, deep links and refresh through `postMessage` and DOM observation, duplicate navigation/state handling, and pay per-frame startup cost. For a one-to-few-person OSS project this was probably the right call; for LifeQuest's desktop shell it is a cautionary example.

**No build step, hand-written everything.** Vanilla ES modules, no framework, no bundler, no TypeScript, hand-rolled Markdown renderers (escaped first, generated tags after), hand-rolled SVG charts, hand-written Jalali conversion, hand-written minimal IMAP4rev1 client (LOGIN/EXAMINE/UID SEARCH/FETCH with literals, cert verification, 2 MB literal cap), and a hand-written MIME parser with RFC 2047 decoding, base64/QP handling and quoted-reply stripping. Remarkably compact and dependency-free; the flip side is that each of these is a bespoke implementation with its own edge cases (e.g. MIME parsing of malformed mail, Jalali leap rules) that a library would have already hardened.

**Security as a feature of the data model.** AAD-bound AES-256-GCM for third-party secrets (`lifeos-mail|user|field` context prevents ciphertext rows from being swapped), outside-web-root key and attachment storage, per-user row scoping, CSRF on every browser write, a fail-closed CSRF helper, a single global API token bound to one account, and a secret-notes flag that the docs explicitly call "not encryption". The team also shipped a security-hardening release (v1.1.0) fixing stored XSS and an open redirect and adding CSP/rate limiting — a mature response pattern.

**AI as an HTTP client, not a privileged component.** The MCP server is a separate Node process that only speaks `/api/v1`; it has no DB/file/config access, strict Zod schemas, destructive annotations, token redaction and URL allowlisting. Reads are consolidated into one `lifeos_query` tool to save context, writes stay as separate tools so clients can require approval per action. That is a clean, auditable architecture. The trade-off is that anything not on the API (Growth, obligations, Todo, boards/columns/labels/comments/attachments) is invisible to the assistant, so the natural-language surface is much smaller than the UI.

**Single-token, single-account multi-user.** Accounts and private workspaces were added (schema v3) but the API token remains bound to one account, every account is an administrator, and admins can reset each other's passwords. The honest docs make this usable for a household or trusted group, not for an organization. It is a good example of shipping a "good enough" multi-user model with explicit limits rather than silently implying isolation.

**Client-computed analytics.** The productivity score, deltas, trends and insights are computed in the browser from cached documents on every dashboard refresh (60 s plus focus/storage events). No analytics tables, no jobs, no storage cost, always in sync with the client's view. The downside is that the number is only as good as the client cache, the weighting is ad hoc (average of non-zero components), and there is no historical record of the score to trend over time.

**Release engineering proportional to a small team.** Docker healthchecks, compose smoke tests, a published-image test that follows the README verbatim, multi-arch publishing, tag-triggered shared-hosting zip, and a broad test workflow. The gaps are equally characteristic: no signed artifacts/checksums, a red Node suite at HEAD, a 50 MB release zip dominated by music, and a long unreleased tail after v1.2.0.

## 14. Limitations, rough edges and missing pieces

- **Marketing drift.** "Ten workspaces" (README), "eleven" (Persian README/site), 12 rows in the README table, and 11 apps + Settings in code. "15 MCP tools" is stale (18 exist). Habittify is advertised with "streaks" but has no per-habit streak counter — the only streak-like visual is the Overview's 16-week completion-density heatmap. Focus advertises "session history" but only stores history for charts; there is no session list. `README`'s "Dates follow Asia/Tehran" is only true for Overview/Growth/Finance/Habittify; Todo's "today" and Kanban reminders use the browser's local time.
- **Arabic is a trap.** `ar` is offered in Settings and `assets/i18n/ar.json` is allowed by the static handler, but the file does not exist: selecting Arabic gives English UI, RTL direction and Arabic-Indic digits. Three tests fail because of it and `docs/languages.md:11` admits it.
- **Red test suite at HEAD.** 6/39 Node tests fail (Persian coverage 15 strings, an expected Persian string, the Arabic dictionary, and a due-alert number-format assertion). CI claims broad coverage but the tree is not green; PHP tests could not be run in this environment, so that remains unverified.
- **API/MCP blind spots.** No bearer API or MCP tool for Todo, Growth, obligations, Calendar, Focus, Email, Weather, boards/columns/labels/comments/checklists/custom fields/attachments, or account management. Todo (`edi_todos_v1`) exists only for the browser. The richest finance feature (debts/credits) is session-only, so the AI cannot answer "what do I owe this month?".
- **Stale/contradictory docs.** `docs/ownership.md` still declares a single-owner installation and "no endpoint promises per-user isolation" even though schema v3 and `docs/accounts.md` implement multi-account private workspaces; `docs/development.md:117` still points to that decision. `docs/accounts.md:45-47` says automated tests were not added for the account changes, while other tests in the tree cover adjacent areas.
- **Dead or half-wired columns/features.** `habits.archived` is filtered everywhere but no UI/endpoint can archive; habit color/icon are fixed in UI (columns exist, `sanitizeColor()` returns a constant); `app_users.role` supports `user` but every account is forced to `admin` (Settings' "Member" branch is unreachable); `legacy_backup_*` rows are write-only archives with no restore UI; `daramd_v1` remains a compatibility mirror that can drift if external clients edit only `daramd_periods_v1`.
- **Concurrency UX is brittle by design.** A stale tab cannot merge; it can only show "copy your edits and reload". External MCP/API edits invalidate open browser documents (409). Notepad history explicitly says to refresh an open page after external changes. For a single user this is acceptable; for a phone + desktop + AI combination it will be felt.
- **No cross-workspace search or export.** Search is per-app; there is no full-text index, no global command palette, no vault export, no PDF/report generation, no backup UI (operator-only `mysqldump` and file copies).
- **No notifications outside an open tab.** Due alerts rely on the browser Notification API without a service worker, so reminders only fire while LifeOS is open; there is no email/push/Telegram delivery and no cron for due alerts (only the optional AI digest cron).
- **No PWA/offline.** The app has no manifest, service worker, offline cache or install prompt; on flaky mobile connections every workspace load is a fresh server round-trip.
- **Money-model limits.** Expense dates lose the year (stored "M j" within a period), no automatic carryover between Persian months, no bank sync/import beyond an Excel shape, no interest/amortization, no per-transaction audit beyond obligations, and the whole ledger lives in one 2 MB JSON document (no pagination).
- **Notepad history grows forever.** Every title/body/format change writes a row; no pruning/retention policy; docs recommend including `notepad_revisions` in backups, which will keep growing.
- **External-dependency sharp edges.** Chart.js and SheetJS come from a public CDN without SRI, so import/export/charts break offline and the supply-chain surface widens CSP; Inter/JetBrains Mono and the RTL Vazirmatn fetch from Google Fonts even though a Vazirmatn copy is bundled.
- **Operational weight.** 53 MB of focus music + 7.8 MB demo GIF in the repo/zip; `git archive` release has no checksum/signature; schema migrations are non-transactional DDL and require coordinated deploys of backend + assets; older code must not run against schema v3.
- **Accessibility gaps remain despite good intentions.** Inline `onclick` handlers in Finance, `'unsafe-inline'` CSP, some unlabeled native selects/date inputs in older apps, chart tooltips via `<title>` only, and no automated a11y test in CI; the dashboard's SVG charts are role="img" with labels but data is not available as a table.
- **Unverified in this audit.** Actual PHP/MySQL runtime behaviour, IMAP/AI/Open-Meteo integration, Docker builds, browser rendering, mobile layout, and MCP tests. Everything above about those is code/doc reading, not execution.

## 15. Top 15 takeaways for LifeQuest (adopt / adapt / defend / ignore)

1. **ADOPT — one read tool plus typed write tools for the agent surface.** LifeOS collapsed 12 near-duplicate read tools into `lifeos_query` with a `type` discriminator and strict per-type argument validation; writes stay individual so each gets an approval prompt. This is a better context-budget pattern than a tool per entity and is directly applicable to Hermes/MCP.
2. **ADOPT — multi-document transactions with ordered row locks and revision checks.** The obligations pay path (commitment decision + ledger entry + revisions for both documents, one MySQL transaction, key-sorted `FOR UPDATE`, retried submissions idempotent) is the strongest engineering artifact in the repo. LifeQuest's Decisions model should learn the "one transaction, all affected documents, return all revisions, adopt atomically" pattern.
3. **ADOPT — per-row AAD-bound AES-256-GCM for third-party secrets.** Context binding (`lifeos-mail|user|field`) stops ciphertext swapping, key file outside the web root with 0600, explicit "lost key = re-enter" guidance. If LifeQuest stores any provider keys or mail credentials, copy this design.
4. **ADOPT — transactional version history for documents.** Notepad snapshots are written inside the same transaction as the state write, capture only content changes, retain deleted text, paginate 50 at a time, and restore with a revision precondition while preserving the overwritten version. This is a cheap, high-trust feature that LifeQuest's notes/decisions history could reuse.
5. **ADOPT — honest documentation of limits, in the product and the README.** "Secret notes are a flag, not encryption", "no per-user tokens/scopes/rate limiting", "every account is an administrator", "Arabic is unfinished". This candour is a trust feature and a competitive advantage over tools that overclaim; LifeQuest should state its own limits as plainly (Hermes requirement, local-first boundaries, what syncs where).
6. **ADOPT — due-date alert taxonomy and per-device dedup.** Overdue / today / coming-up grouping, 09:00 defaults for date-only items, a 6-hour notification window so old items never replay, reminder offsets 5/60/1440, shown-key dedup in localStorage with 14-day cleanup, and an explicit "notifications only while open" note. The logic is portable even if the transport changes.
7. **ADAPT — six fixed life dimensions + guided reviews.** The fixed taxonomy (spirituality, health, relationships, finance, self-growth, fun & rest) and the eight-step weekly/monthly/quarterly review with "previous next step" and save-time snapshots are a good reflection model. Adapt by making dimensions configurable rather than fixed, and keep the no-composite-wellbeing-score stance.
8. **ADAPT — habit-linked goal progress with attendance left in one place.** Habit goals derive progress from `habit_logs` (distinct dates in window / target, capped at 99 until met), never duplicate tasks, and still count archived-habit history. If LifeQuest links habits to goals, keep attendance single-sourced exactly like this.
9. **ADAPT — the hybrid storage split.** SQL tables for relational/queried data (habit logs, attachments, mail, revisions) and JSON documents for document-shaped workspaces is a pragmatic middle ground for a local-first vault. Adapt it with explicit document schemas/versioning and a migration path, because LifeOS's untyped documents are its biggest long-term liability.
10. **ADAPT — outside-web-root file storage with session-checked serving.** Attachments are stored in a hashed directory beside the backend, referenced by 32-hex ids, served only through an authenticated endpoint that filters on owner, with sanitized filenames and a hard size cap. LifeQuest's vault should keep user files out of any static/public path and serve through an authenticated layer.
11. **DEFEND — revision conflict UX and the single-writer assumptions.** LifeOS's answer to concurrency is "409, copy your edits, reload" with no merge; Todo has no conflict surface at all; notepad asks users to refresh after external changes. LifeQuest's local-first model and Decisions approval flow should be defended as a better answer to multi-device/AI concurrent editing, and the benchmark report should say so explicitly.
12. **DEFEND — local-first ownership and no third-party runtime dependencies.** LifeOS is self-hosted but still depends on jsDelivr, Google Fonts, Open-Meteo, and a live PHP/MySQL host; there is no offline mode. LifeQuest's vault-on-disk + desktop shell can credibly claim offline, no-CDN, no-server ownership — a real differentiator to sharpen in positioning.
13. **DEFEND — the desktop-grade UI surface.** Hand-rolled SVG charts, time-of-day Focus scene, infinite notes canvas with cursor-centered zoom and per-block RTL, a real Markdown/HTML notepad with sandboxed previews: this is a high bar for a PHP app and a reminder that LifeQuest's Electron/React UI must not feel thinner than a self-hosted PHP dashboard.
14. **IGNORE (or deliberately skip) — iframe-per-workspace architecture.** It enabled fast parallel growth but produces duplicated CSS/i18n/state plumbing, three translation passes, and cross-frame messaging hacks. Adopt the isolation goal (separate state keys, app-owned documents) without copying the iframe implementation.
15. **IGNORE — the vanity metrics and marketing pattern.** "Ten workspaces" while shipping eleven, "15 tools" while shipping 18, "streaks" without streaks, a productivity "score" that averages only non-zero components and omits goals from its week-over-week baseline: these are exactly the overstatements LifeQuest's benchmark should call out and avoid. Compete on verifiable, inspectable behaviour, not badge counts.
