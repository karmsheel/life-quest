# Design: MCP agent pairing

**Date**: 2026-10-03
**Status**: Draft for review. Architecture, call flow, error handling, and the end-to-end test were approved in conversation on 2026-10-03.

## Problem

The MCP door is plain HTTP on `127.0.0.1:8643` with no credential. Every caller is logged as the companion and can read the whole open vault. A process that can reach loopback, including one that arrived through a tunnel, is indistinguishable from Hermes.

Operators will run LifeQuest on a machine they reach from a laptop, and will talk to it through agents on a phone. Those agents need a way in. The way in has to name the caller, start with no vault access, and grow only by an operator grant.

## Settled choices

- Two doors, both on `127.0.0.1`. `8643` is the local door. `8646` is the invite door. LifeQuest does not listen on a public address, does not terminate TLS, and does not bind a private-network interface. The operator forwards `8646` through a path they already trust (Tailscale, WireGuard, or SSH).
- The companion stays pre-paired and keeps today's full tool surface, today's write rules, and the desktop's current domain lens.
- Every other MCP client is a connected agent. The first accepted introduction files one pairing Decision. Until that Decision is approved, the client gets no tools and no vault data.
- Approval starts the agent read-only, with no domains and Schedule off.
- Write, once granted, uses the companion's write rules inside the assigned domains. Schedule is a separate switch and starts off.
- Reads follow the same domain list. Records with no domain stay with the companion.
- The Hermes hire list is unchanged. A connected agent is a different roster from a scanned hire.
- Permission edits in Personnel are direct operator actions. The pairing Decision is the only new Decision this feature adds.

## Doors

Both doors speak the existing Streamable HTTP MCP on `POST /mcp`. Any other method or path returns 404. Each door binds independently. If `8646` is already taken, the vault still opens, `8643` still serves the companion, and Settings says the invite door is down. If `8643` is already taken, Settings keeps today's port-in-use error. Quitting LifeQuest closes both listeners.

The socket address is not identity. A tunnel that lands on localhost is still the door it connected to.

Opening a vault binds both doors to that vault. Switching vaults rebinds them to the newly opened vault's root, roster, and companion credential. The door serves one vault, the one that is open.

### Who is calling

Every request carries `Authorization: Bearer <token>`.

The companion token is generated by LifeQuest, once per vault, and stored in app userData so the profile can be rewritten. `ensure` writes it into the `lifequest` Hermes profile as:

```yaml
mcp_servers:
  lifequest:
    url: http://127.0.0.1:8643/mcp
    headers:
      Authorization: Bearer <companion-token>
```

Existing keys on that server entry stay. Other `mcp_servers` entries stay. A later `ensure` refreshes the header to the stored companion token. The companion token is accepted on either door and always takes the companion path. A request with no bearer, or with a bearer LifeQuest does not know, is never treated as the companion.

A connected agent chooses its own bearer and keeps it. LifeQuest stores only the SHA-256 hex hash. The fingerprint the operator sees is the first 12 hex characters of that hash. A bearer shorter than 22 characters is refused with `AUTH_REQUIRED`. The raw bearer and the raw invite code are never written to the vault, the life log, or an error message.

The display name arrives in `X-LifeQuest-Name` on first contact. LifeQuest trims it and accepts 1 to 80 characters.

The invite code arrives in `X-LifeQuest-Invite`. Personnel mints it. It is 128 bits, shown once, stored only as a SHA-256 hash, single-use, and expires 24 hours after mint. Personnel can drop an unused code. A code is consumed only when it actually introduces a new agent. A missing name, an already-known bearer, or a pairing list that is already at its pending cap leaves the code unused.

### First contact

| Door | Request | Result |
|---|---|---|
| Either | No bearer, or a bearer shorter than 22 characters | HTTP 401 `AUTH_REQUIRED`. Nothing is filed. |
| `8643` | New bearer, no acceptable name | HTTP 401 `NAME_REQUIRED`. Nothing is filed. |
| `8643` | New bearer and an acceptable name | One pending pairing Decision. |
| `8646` | Unknown bearer, no invite code, or a blank code | HTTP 401 `INVITE_REQUIRED`. Nothing is filed. |
| `8646` | Invite code used, expired, or unknown | HTTP 401 `INVITE_INVALID`. Nothing is filed. |
| `8646` | Valid unused code, new bearer, no acceptable name | HTTP 401 `NAME_REQUIRED`. The code stays unused. |
| `8646` | Valid unused code, new bearer, acceptable name | The code is consumed. One pending pairing Decision. |
| Either | A bearer that is already pending, rejected, or revoked | No new Decision. The code on an invite request stays unused. |
| Either | A new introduction while 20 pairing rows are already pending | HTTP 429 `PAIRING_LIMIT`. Nothing is filed. A valid invite code stays unused. |

The pending cap counts roster rows with status `pending`. Repeat calls with the same bearer reuse the same row.

An accepted introduction answers `initialize` successfully. `tools/list` is empty and `tools/call` returns `PAIRING_PENDING`.

Pairing is serialized on the vault queue so two simultaneous first contacts with the same bearer create one row.

For a known bearer, `initialize` succeeds so the client keeps its configuration. `tools/list` and `tools/call` then follow the roster, as specified under Errors.

## Roster and secrets

The vault file `.lifequest/connected-agents.json` holds the roster and no secrets:

```ts
type ConnectedAgent = {
  id: string;
  name: string;
  fingerprint: string;
  status: "pending" | "active" | "rejected" | "revoked";
  access: "read" | "write";
  domainSlugs: string[];
  schedule: boolean;
  door: "local" | "invite";
  createdAt: string;
  decidedAt: string | null;
};
```

A new row starts `pending`, `access: "read"`, `domainSlugs: []`, `schedule: false`. `door` records which door introduced it.

App userData `connected-agent-secrets.json` is keyed by vault id and holds the raw companion token, the hash of each connected-agent bearer, and the invite-code hashes with expiry and used-at. Hashes for rejected and revoked agents stay, so that bearer cannot introduce itself again. A new bearer is a new agent.

## Pairing Decision

The target is `{ type: "agent-pairing", agentId: string }`.

`normalizeDecision` parses that target. An unrecognized target must not fall through to a library note.

The Decision title is `Connect <name>`. The body shows the fingerprint and the door (`local` or `invite`). Approve and reject use the existing Decision buttons.

Approve sets the row `active`, leaves it read-only with no domains and Schedule off, and sets `decidedAt`. Reject sets the row `rejected`, sets `decidedAt`, and leaves the bearer hash in place. A second approve on an already-active row changes nothing.

There is no approve control on the Personnel card. A pending row there reads "Waiting for approval" and shows the name and fingerprint.

## Personnel

Personnel order:

1. **Companion.** A fixed card: Hermes, full access, the open vault's companion. It has no domains editor, no Write switch, no Schedule switch, and no revoke.
2. **Connected agents.** Pending and active rows. Invite, domain assignment, Write, Schedule, and Revoke live here.
3. **Scan and active hires.** Unchanged.

An active row has a multi-select of live domains, a Write switch, a Schedule switch, and Revoke. Assignment accepts a live domain only. A domain that is later archived drops out of the effective grant while it stays archived. Revoke sets `revoked` and keeps the bearer hash. Rejected and revoked rows stay in the file and are omitted from this list.

Minting an invite shows the code once in the panel, with its expiry.

## Permission gate

The gate runs before `executeTool` on every connected-agent call. The companion bearer skips the gate.

The desktop lens is the companion's lens. A connected agent's grant is its own `domainSlugs`, `access`, and `schedule`. Edits in Personnel apply on the next call.

`tools/list` contains only tools the grant allows. A call to anything else returns `FORBIDDEN` and writes nothing.

An active agent with an empty domain list and Schedule off gets `NO_GRANT` and an empty tool list.

### Domain reads

With at least one assigned live domain, the agent may read doctrine, databases, pages, script-block results, goals, events, projects, library notes, domain-scoped reviews, and the domain slice of a period pack.

A library note is included only when it has at least one domain and every one of those domains is assigned. A goal, event, or project with no domain stays with the companion. A review tool or period pack whose scope is `overall` stays with the companion. `list_decisions` returns decisions whose domain list is non-empty and entirely inside the assignment. Pairing decisions and decisions with no domain are omitted.

A read of one record outside the grant returns `NOT_FOUND`. List tools omit those rows.

`get_state` for a connected agent returns events in the assigned domains. It includes tasks and the live week only when Schedule is on. It omits About me, years, month objectives and notes, the day-type catalog, and events with no domain.

`get_period_pack` is allowed only when `scope` is an assigned live domain. Tasks and live days are removed unless Schedule is on. The previous review and the overall section list are removed.

### Domain writes

Write uses the companion's current rules inside the assigned domains.

These still file a Decision and do not land until the operator approves them: doctrine, library notes, goals, and projects. A database write follows the companion. If the companion would file a Decision, the connected agent files a Decision. If the companion would apply a new row immediately because that database is on the insert allowlist, the connected agent does too, when Write is on and the database's domain is assigned. Updates, deletes, new databases, and new columns stay pending, as they do for the companion.

Event create, update, and delete run immediately when the event's domain is an assigned live domain, matching the companion.

Capture, undo, and correct run immediately, and only when Write is on and `financial` is an assigned live domain.

Script-block application still writes the page directly, as it does for the companion, and only when Write is on and the page's domain is assigned. A script-block read requires the page's domain to be assigned.

Creating a record, or moving one, onto a missing domain, a null domain, an archived domain, or a domain outside the assignment returns `FORBIDDEN` and files nothing.

### Schedule

Schedule off removes task tools, live-week tools, and the task and live-day fields of `get_state` and `get_period_pack`.

Schedule on allows reads of tasks and the live week.

Write plus Schedule posts tasks and live-week edits immediately. The live-week tools are `set_week_day_type`, `set_week_day_items`, `set_week_weekly_items`, `place_grid_block`, `clear_grid_block`, and `reset_week`. The task tools are `create_task`, `update_task`, and `delete_task`.

Day-template tools (`create_day_type`, `update_day_type`, `delete_day_type`, `set_default_weekday_type`, `set_default_weekly_items`) are available only when Schedule and Write are both on, and they still file a Decision.

An agent with Schedule on and no domains receives the schedule tools only.

### Companion-only tools

These stay on the companion: `create_year`, `delete_year`, `set_month_day`, `set_month_objectives`, `set_month_notes`, `set_about_me`, and any later tool that has no domain and is not part of Schedule. A connected agent that calls one gets `FORBIDDEN`.

### Life log

A connected-agent call records `{ type: "agent", id, name }` from the roster row. The agent cannot choose a different actor.

## Errors

Auth failures end at the HTTP door. A recognized agent outside its grant gets a tool result and stays connected.

| Code | When |
|---|---|
| HTTP 401 `AUTH_REQUIRED` | No bearer, or a bearer shorter than 22 characters. A profile whose companion header is missing gets this until `ensure` writes the header. That request is not a pairing attempt. |
| HTTP 401 `NAME_REQUIRED` | A new bearer arrived without an acceptable name. |
| HTTP 401 `INVITE_REQUIRED` | An unknown bearer on `8646` sent no invite code. |
| HTTP 401 `INVITE_INVALID` | The invite code is used, expired, or unknown. |
| HTTP 429 `PAIRING_LIMIT` | A new introduction would exceed 20 pending pairing rows. |
| Tool `PAIRING_PENDING` | The Decision is still open. The tool list is empty. |
| Tool `PAIRING_REJECTED` | The operator rejected that key. |
| Tool `PAIRING_REVOKED` | The operator revoked that key. |
| Tool `NO_GRANT` | The agent is active, has no live domain, and Schedule is off. |
| Tool `FORBIDDEN` | The tool, domain, or Schedule switch is outside the grant. |
| Tool `NOT_FOUND` | A read of one record outside the grant. Same shape as a missing record. |

`PAIRING_REJECTED` and `PAIRING_REVOKED` do not open a new Decision for that bearer.

## Settings

Settings → Hermes shows both doors while a vault is open:

- Local: `http://127.0.0.1:8643/mcp`
- Invite: `http://127.0.0.1:8646/mcp`

A door that failed to bind shows its own error. The other door's URL stays.

## Verification

One end-to-end test drives both doors over HTTP against a temporary vault, then reads the vault and the life log. It writes `pairing-e2e.json` in that vault. The test fails if any scenario disagrees with the table below, or if the raw bearer or the raw invite code appears anywhere in the vault tree. That file is the artifact for the run.

The scenarios:

- No bearer returns `AUTH_REQUIRED` and leaves the vault unchanged.
- A new local bearer is `PAIRING_PENDING`, files exactly one pairing Decision, and a second call files no second Decision. `tools/list` is empty and a read returns no vault data.
- An unknown bearer on `8646` with no code returns `INVITE_REQUIRED` and files nothing. A used or expired code returns `INVITE_INVALID`. A valid code files one pending Decision and cannot be used again. A valid code with no name returns `NAME_REQUIRED` and leaves the code unused.
- The 21st pending introduction returns `PAIRING_LIMIT`, on either door. An invite code presented with that introduction stays unused.
- After approval, with no domains and Schedule off, the agent returns `NO_GRANT`.
- A read-only agent assigned to `financial` can read that domain's doctrine and rows. A write tool returns `FORBIDDEN` and files no Decision. Capture returns `FORBIDDEN`. A direct read of a health row returns `NOT_FOUND`. A library note tagged with both domains is omitted.
- Write on, still only `financial`, with the finance kit installed, one transactional account, and an empty insert allowlist: a clear capture posts, a database change files a Decision and does not write the row, and an event with no domain returns `FORBIDDEN`.
- Schedule off: `get_state` and `get_period_pack` contain no tasks and no live days. Schedule on and Write on: a task posts immediately, and a day-template change files a Decision.
- A rejected or revoked bearer stays in that status and does not open a new Decision.
- The life log records the connected agent's id and name.
- The companion bearer still reads and still files a normal doctrine Decision. A missing companion header returns `AUTH_REQUIRED`.
- With the invite port already taken, the local door still answers the companion.

## Out of scope

A public listener, TLS, certificates, and binding a Tailscale or WireGuard address. Per-tool grants beyond Read/Write, the domain list, and Schedule. A connected agent editing its own grant. Merging connected agents into Hermes hires. A phone client. Automatic rotation of the companion token on every launch.

- `apps/desktop/electron/companion-profile.ts` — the companion `Authorization` header.
